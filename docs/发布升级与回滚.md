# 发布、升级与回滚

## 版本与渠道

- 开发版本：`X.Y.Z-SNAPSHOT`，不得发布到默认渠道。
- Alpha：内部或小范围验证，允许功能不完整，但安全边界和数据写入必须可验收。
- Beta：功能冻结，完成自动化矩阵和主要人工路径，处理反馈后才能晋级。
- RC：与计划正式版使用相同代码、签名、SBOM 和安装包，只允许发布阻断问题修复。
- 正式版：`X.Y.Z`，发布到 `default` 渠道；同一版本号不得重建后覆盖。

预发布渠道通过 `-PpluginChannel=alpha|beta|rc` 指定。版本号必须唯一，并与 Git 标签 `vX.Y.Z` 或预发布标签一致。

## 本地候选包

```bash
mvn --batch-mode --file samples/java-mybatis-minimal/pom.xml clean verify
mvn --batch-mode --file samples/semantic-corpus/pom.xml clean verify
./gradlew clean check verifyPluginProjectConfiguration verifyPluginStructure verifyPlugin \
  -PpluginVersion=1.0.0-rc.1
```

该命令生成未签名 ZIP、CycloneDX JSON/XML 和全部测试报告。本地无发布密钥时仍可完成开发构建与验证，但不能把未签名包声明为正式发布包。

## CI 签名与发布

发布工作流只从 GitHub Actions Environment secret 读取以下值：

- `CERTIFICATE_CHAIN`
- `PRIVATE_KEY`
- `PRIVATE_KEY_PASSWORD`
- `PUBLISH_TOKEN`（仅发布 JetBrains Marketplace 时需要）

环境与凭据归属固定如下：

| Environment | 凭据 | 用途 |
|---|---|---|
| `release-signing` | `CERTIFICATE_CHAIN`、`PRIVATE_KEY`、`PRIVATE_KEY_PASSWORD` | 对构建阶段产生的精确 ZIP 签名并验证 |
| `release-github` | 无发布 secret | 审批并创建/公开 GitHub Release |
| `marketplace-preview` | `PUBLISH_TOKEN` | Alpha/Beta/RC 预发布渠道 |
| `marketplace-production` | `PUBLISH_TOKEN` | `default` 正式渠道 |

当前四个环境和审批规则已建立，但 secret 尚未配置。维护者应在 GitHub 仓库的 Settings → Environments 中录入，不得把值粘贴到 issue、PR、聊天、命令历史或仓库文件。

私钥、证书密码和 Marketplace token 不得写入仓库、Gradle 属性、日志、设置导出、SBOM 或构建产物。缺少签名 secret 时，发布工作流必须失败；普通 `check` 和本地开发构建不受影响。

推送 `v*` 标签会先校验版本/渠道、精确 CHANGELOG 段、触发时 `origin/main` 提交和同一 SHA 的全部必需检查；随后构建唯一未签名 ZIP、SBOM、metadata 与 SHA-256，在 `release-signing` 环境审批后对同一 ZIP 签名、验签和生成来源证明，最后在 `release-github` 环境审批后创建 GitHub 草稿 Release。仓库已配置 `v*` 标签保护与 immutable releases；这两项防篡改配置不能替代签名和实机验收。

Marketplace 发布只能手动触发独立工作流，并显式选择预发布或正式环境。工作流从草稿 Release 下载唯一已签名 ZIP，重新校验 SHA-256、metadata、插件身份和 GitHub 来源证明，发布成功后再次复核制品再公开 GitHub Release；不会重新构建或重新签名。

首次 Marketplace 上架必须由维护者人工初始化插件条目并决定是否勾选 `Hidden`。建议用独立且唯一的 bootstrap 版本（例如 `0.1.0-alpha.1`）完成首次人工上传，后续自动化从递增版本继续；不要对人工上传过的同一版本重跑发布，因为 Marketplace 不允许覆盖同版本。`Hidden` 只能在首次上传时选择，一旦公开不能重新隐藏，公开动作应视为不可逆审批。

## 发布操作顺序

1. 在 GitHub 四个 Environment 中配置所需 secret；只在仓库 UI 中录入，不通过聊天传递。
2. 首次上架时，人工上传唯一 bootstrap 版本并决定 `Hidden`；记录 Marketplace 插件 ID/条目已存在，不复用该版本。
3. 让准备发布的提交先进入 `main`，确认同一 SHA 的主 CI、CodeQL、三系统、100 次生命周期、5/5 隔离和五宿主兼容检查全部成功。
4. 在 `main` 当前精确提交创建受保护的 `vX.Y.Z[-alpha.N|-beta.N|-rc.N]` 标签；标签不得指向分支旧提交。
5. 在 Actions 中批准 `release-signing` 与 `release-github`；核对草稿 Release 的版本、release notes、唯一签名 ZIP、SBOM、metadata、SHA-256 和来源证明。
6. 需要 Marketplace 时手动运行发布工作流，选择 `marketplace-preview` 或 `marketplace-production` 并批准对应环境；成功后由工作流公开 GitHub Release。
7. 在副屏或独立测试机完成安装、升级、降级、禁用、卸载和 15 分钟首次使用路径，再决定是否晋级渠道。

## 升级验收

每个 Alpha、Beta、RC 和正式候选都要在干净沙箱和保留设置的升级沙箱分别验证：

1. 从当前最低受支持版本安装旧包并启动；
2. 配置非默认但不含敏感信息的 schema v1/v2 设置，关闭 MCP；
3. 升级到候选包，确认导航、检查、补全、设置迁移和默认离线状态；
4. 启用 MCP，只核对回环地址、令牌旋转、白名单和关闭后端口释放；
5. 禁用、启用、重启、卸载并确认项目文件未被隐式修改；
6. 在 IntelliJ IDEA 2026.1、当前最高支持稳定版和 Android Studio 支持版本重复核心路径。

图形界面测试只能在不会占用用户主屏幕的副屏或独立测试环境执行。没有副屏时只记录为“待验”，不能以平台单元测试代替真实安装、升级和卸载证据。

## 降级与回滚

- 回滚前导出非敏感设置并备份项目；导出文件不包含 JDBC 密码和 MCP 令牌。
- 先禁用 MCP 并关闭项目，使监听端口、会话和预览令牌失效。
- 从 IDE 卸载候选版本，安装上一个已签名、SHA-256 已核对的版本，再重启 IDE。
- 新版本写出的未来 schema 设置会被旧版或当前版导入器整体拒绝；不要手工删字段后强行导入。必要时恢复默认设置，再逐项重配。
- 插件索引和缓存可以重建；项目源码、用户生成文件和数据库变化不应依赖卸载自动回滚。所有写操作仍应使用 IDE Undo、Local History 或版本控制恢复。
- 若 Marketplace 更新有阻断问题，停止后续渠道、保留证据并发布递增版本的修复包，绝不以相同版本号替换既有制品；已公开插件不能依靠重新勾选 `Hidden` 回滚。

## 发布阻断条件

存在以下任一项时不得公开正式版：自动化质量门失败、Verifier 不兼容、签名未验证、SBOM/许可证不完整、产物发现密钥或凭据、写入无法撤销、隐私说明与实际行为不符、支持矩阵未验、升级/降级/卸载实机证据缺失或仍有 P0/P1 问题。
